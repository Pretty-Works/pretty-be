# 인물 페르소나 작성 규격

> 280명을 서로 다른 사람으로 만들되, 사번·이메일·나이·입사일은 기계적으로 검증 가능해야 한다.
> 이 문서는 **생성 규칙**과 **카드 포맷**을 정한다. 여기서 벗어난 카드는 다시 쓴다.
> **2026.08 개정** — 원래 500명 설계에서 280명으로 축소했다(01번 문서 참고). 전출조 180명은 창립 사실이라 그대로 두고, 이후 공채·경력 채용 규모만 줄였다.

---

## 1. 식별자 생성 규칙

### 1.1 사번 (`employee_no`, 로그인 ID)

```
DT + 입사연도 2자리 + '-' + 그 해 입사 순번 4자리
예) DT22-0001   DT24-0087   DT26-0031
```

- 연도별로 0001부터 다시 시작한다. 연도 prefix가 있어 전사 유일성이 보장된다.
- 부서 코드를 넣지 않는다. **부서 이동 시 사번이 바뀌면 안 되기 때문이다.**
- 2022년 순번은 창립 전출조(180명) → 공채 1기 → 경력 입사 순.

| 연도 | 범위 | 인원 | 구성 |
|---|---|---|---|
| 2022 | `DT22-0001` ~ `DT22-0199` | 199 | 전출조 180 + 공채1기 10 + 경력 9 |
| 2023 | `DT23-0001` ~ `DT23-0026` | 26 | 공채2기 12 + 경력 14 |
| 2024 | `DT24-0001` ~ `DT24-0025` | 25 | 공채3기 13 + 경력 12 |
| 2025 | `DT25-0001` ~ `DT25-0021` | 21 | 공채4기 14 + 경력 7 |
| 2026 | `DT26-0001` ~ `DT26-0009` | 9 | 경력 9 (8월 1일까지) |
| | | **280** | |

> 이미 리더십 21명 + 완료 부서 인원에 배정된 사번 중 이 범위를 넘는 경우가 있다(예: 2023년에 `DT23-0045`까지 부여된 상태). 이건 500명 설계 당시 부여분이라, 280명으로 정리(트리밍)하면서 범위 안으로 맞춘다 — 잘려나가는 사람의 사번은 결번으로 남는다.

### 1.2 이메일 (`email`)

```
<이름 로마자>.<성 로마자>@daontech.co.kr   — 전부 소문자
예) 오현주 → hyunju.oh@daontech.co.kr
    남기훈 → kihoon.nam@daontech.co.kr
```

- 로마자는 국어의 로마자 표기법을 따른다. `ㅓ`=eo, `ㅡ`=eu, `ㅕ`=yeo, `ㅐ`=ae.
- **동명이인을 만들지 않는다.** 280명 전원 고유 이름을 쓴다. 검색·멘션 데모에서 혼선이 나지 않게 하려는 의도적 제약이다.

### 1.3 전화번호 (`phone_number`)

```
010-4[사번 뒤 3자리]-[생일 MMDD]
예) DT22-0001, 1971-06-14 → 010-4001-0614
```

가상 번호임을 분명히 하기 위한 조합 규칙이다. 내선은 `02-6200-[사번 뒤 4자리]`.

### 1.4 이름 (`name`)

- 성씨는 실제 인구 분포를 따른다: 김 21%, 이 15%, 박 8%, 최 5%, 정 5%, 강·조·윤·장·임 각 2~3%, 나머지 성씨 다양하게.
- 이름은 세대별 유행을 반영한다.

| 출생 연대 | 이름 톤 | 예 |
|---|---|---|
| 1970년대 | 한자식 2음절 | 영달, 준혁, 정선, 기훈 |
| 1980년대 | 중간 | 동렬, 유진, 미르, 세희 |
| 1990년대 | 부드러운 한자·중성적 | 서윤, 지호, 도연, 하람 |
| 2000년대 | 순우리말·개방형 | 하윤, 이든, 시안, 유하 |

| 인사 | 8 | 6 | 75% | |
| 재무 | 8 | 5 | 63% | |

| **합계** | **280** | **100** | **36%** | |

### 1.6 생년월일 (`birth_date`) — 직급별 연령 분포

2026년 8월 1일 기준 만 나이.

| 직급 | 출생 연도 | 나이 | 중앙값 |
|---|---|---|---|
| 사원 | 1995~2002 | 24~31 | 27 |
| 선임 | 1988~1998 | 28~38 | 32 |
| 파트장 | 1983~1993 | 33~43 | 37 |
| 팀장 | 1976~1986 | 40~50 | 44 |
| 임원 | 1970~1980 | 46~56 | 49 |
| 부사장 | 1974 | 52 | — |
| 사장 | 1971 | 55 | — |

- 월·일은 고르게 흩는다. 1월 1일·12월 31일 같은 경계일은 피한다.
- **나이 역전을 일부러 넣는다.** 파트장보다 나이 많은 선임, 팀장보다 나이 많은 파트장이 실제로 존재한다. 수평 호칭 문화에서 이 역전이 만드는 미묘함이 카드의 재료다.

### 1.7 입사일 (`hire_date`)

| 유형 | 인원 | 입사일 |
|---|---:|---|
| **전출조** (물적분할 이관) | 180 | `2022-03-02` 전원 동일 |
| 공채 1기 | 10 | `2022-09-01` |
| 공채 2기 | 12 | `2023-09-01` |
| 공채 3기 | 13 | `2024-09-02` |
| 공채 4기 | 14 | `2025-09-01` |
| 경력 수시 | 51 | 매월 1일 또는 16일 (2022-04-01 ~ 2026-07-16) |

> 전출조 180명이 280명 중 64%나 차지하는 이유. 원래(500명 설계) 대비 성장폭을 줄였을 뿐 창립 규모(180명)는 역사적 사실이라 안 건드렸다 — 그 결과 "덜 폭발적으로 성장한 회사는 창립 세대 비중이 더 오래 유지된다"는, 오히려 더 자연스러운 그림이 됐다.

- 공채 5기(2026-09-01)는 아직 입사 전이라 280명에 없다.
- 전출조 180명은 회사 정체성의 핵심이므로 **부서별 배분을 고정**한다.

| 부서 | 전출조 | 부서 | 전출조 |
|---|---:|---|---:|
| 경영지원 | 6 | 품질보증 | 16 |
| 인사 | 4 | DevOps | 9 |
| 재무 | 5 | Infra | 12 |
| 영업 | 7 | Data | 13 |
| 사업기획 | 6 | Security | 7 |
| 컨설팅 | 8 | FE | 21 |
| PM | 14 | BE | 52 |
| | | **합계** | **180** |

> **280명 축소판.** Infra은 500명 설계 당시 이미 전출조 22명을 실명으로 확정해뒀는데, 새 부서 정원(18명)이 그보다 작아 자리가 안 났다. Infra에서 10명만큼 줄이고, 그 여유분을 아직 안 쓴 부서(PM+2·품질보증+2·FE+2·BE+2·Data+2)에 나눠 옮겨서 합계 180을 유지했다. Infra 트리밍(과제 #6) 때 전출조 12명만 남기고 정리한다.

### 1.8 재직 상태 (`status`)

기본은 전원 재직(`EMPLOYED`). 다만 `StatusType` 검증과 퇴사자 처리 데모를 위해 **280명 외에 퇴사자 7명**을 별도 부록으로 둔다(색인 문서 부록 A). 이들은 정원 280에 포함되지 않는다.

## 2. 카드 포맷

### 2.1 A형 — 풀 프로필 (약 60명)

대상: 사장·부사장·임원 7명 + 팀장 14명 + 서사가 필요한 파트장·핵심 선임 약 40명.

```markdown
### 오현주 · 사장 · 경영지원

| 사번 | DT22-0001 | 생년월일 | 1971-06-14 (55세) |
|---|---|---|---|
| 이메일 | hyunju.oh@daontech.co.kr | 전화 | 010-4001-0614 |
| 입사 | 2022-03-02 (전출조) | 소속 | 대표 직속 |

**한 줄** — 한 문장으로 이 사람을 설명한다.

**배경** — 학력·이전 경력·이 회사에 온 경위. 3~5문장.

**성격** — 무색한 형용사 대신 관찰 가능한 행동으로. 3~5문장.

**업무 스타일** — 일을 받는 방식, 결정하는 방식, 문서/회의 습관, 갈등 처리. 4~6문장.

**강점 / 약점** — 각 2~3개. 약점은 실제로 아픈 것으로.

**사람 관계** — 누구와 가깝고 누구와 부딪히는지. 실명으로.

**지금 맡은 일** — 2026년 8월 현재. 프로젝트명으로.

**PrettyWorks** — 이 사람이 이 툴을 어떻게 대하는가. 열심히 쓰는지, 시늉만 하는지, 대놓고 안 쓰는지. 어떤 화면에 오래 머무는지. 데모 시연의 시점이 여기서 나온다.

**자주 하는 말** — 실제 발화 1~3개. 따옴표로.
```

### 2.2 B형 — 표준 카드 (약 220명)

대상: 나머지 전원. 10~12줄.

```markdown
#### 김서윤 · 선임 · BE (여신파트)
`DT23-0041` · 1994-03-22 (32세) · 여 · seoyun.kim@daontech.co.kr · 010-4041-0322 · 2023-05-16 입사(경력)

- **성격** 키워드 3개 — 짧게. 서로 안 겹치게.
- **업무 스타일** 2~3문장. 코드/문서/회의에서 드러나는 구체적 습관.
- **강점** 한 줄. **약점** 한 줄.
- **협업** 한 줄. 누구와 어떻게 일하는가.
- **지금** 한 줄. 맡고 있는 프로젝트·업무.
- **PrettyWorks** 한 줄. 이 툴을 어떻게 쓰는가 (또는 왜 안 쓰는가).
- **한 컷** 한 줄. 이 사람을 기억하게 만드는 장면 하나.
```

## 3. 작성 원칙

카드 220장이 템플릿처럼 읽히지 않게 하는 규칙이다.

1. **MBTI를 쓰지 않는다.** 16종으로 280명을 나누면 그 순간 납작해진다.
2. **무색 형용사 금지.** "성실하다, 꼼꼼하다, 책임감 있다"는 쓰지 않는다. 대신 *"PR 설명란을 세 문단씩 쓴다"*, *"회의 끝나고 5분 안에 요약을 올린다"* 처럼 행동으로 쓴다.
3. **한 파트 안에서 성격 키워드를 겹치지 않게 한다.** 파트는 3~12명이라 관리 가능하다.
4. **전원이 유능할 수 없다.** 평가 등급 분포(S 10 / A 25 / B 50 / C 12 / D 3%)를 실제로 반영한다. 저성과자 42명, 최하위 8명이 280명 안에 있어야 한다. 번아웃, 이직 준비, 사내 정치, 조용한 퇴사도 비율대로 넣는다.
5. **모두를 갈등 축 위에 놓는다.** [`00-회사-개요.md` §13](00-회사-개요.md#13-회사-내부의-갈등-축)의 여섯 축 중 최소 하나에 대해 이 사람이 어느 편인지 드러나야 한다.
   특히 6번 축(가시화 = 관리인가 감시인가)은 **도입 2년이 넘도록 완전히 가라앉지 않은** 온도라서, 280명 중 상당수가 여기에 대한 입장을 갖는다.
6. **관계는 실명으로 건다.** "동료와 잘 지낸다"가 아니라 "박지훈 파트장과 코드 리뷰에서 매번 붙는다".
7. **한 컷은 반드시 구체적인 장면으로.** 습관·소지품·말버릇·사건 중 하나.
8. **차별적 고정관념을 성격에 쓰지 않는다.** 성별·나이·출신 지역·학력으로 성격을 설명하지 않는다. 개인의 경험과 선택으로 쓴다.

## 4. DB 매핑

카드의 각 필드는 `users` 테이블에 그대로 대응한다. 나중에 시드 SQL로 변환할 때 손실이 없어야 한다.

| 카드 필드 | 컬럼 | 타입 | 비고 |
|---|---|---|---|
| 사번 | `employee_no` | VARCHAR(20) | UNIQUE, 로그인 ID |
| — | `password_hash` | VARCHAR(255) | 시드 시 전원 동일 BCrypt (`Daon!2026`) |
| 이름 | `name` | VARCHAR(20) | |
| 이메일 | `email` | VARCHAR(100) | UNIQUE |
| 전화 | `phone_number` | VARCHAR(20) | |
| 생년월일 | `birth_date` | DATE | |
| 성별 | `gender` | VARCHAR(10) | `GenderType` |
| 부서 | `department` | VARCHAR(30) | `DepartmentType` 14종 |
| 직급 | `position` | VARCHAR(30) | `PositionType` 7종 |
| 재직 상태 | `status` | VARCHAR(20) | `StatusType` |
| 입사일 | `hire_date` | DATE | |

**DB에 없는 정보** — 본부, 팀, 파트, 성격, 업무 스타일, 관계, 프로젝트. 이것들은 문서에만 존재한다. 팀·파트는 `projects`·`project_members` 로, 관계는 프로젝트 배정으로 간접 표현할 수 있다.
